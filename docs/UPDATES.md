# Updates and first-run downloads

## What 3re checks, and what it sends

When "Check for updates once a day" is on (Settings → Updates; on by default, can be turned off), 3re asks GitHub
for the list of 3re releases once a day: `GET https://api.github.com/repos/<owner>/<repo>/releases`. The request
carries the User-Agent `3re-update` and nothing else: no account, no identifier, no version, no usage data, no
cookies. "Check now" does the same on demand. Nothing is downloaded or installed until you confirm.

## Channels

| Channel | Offers |
|---|---|
| Stable | releases that are not marked pre-release (and whose version has no `-alpha`, `-beta`, …) |
| Alpha | every newer release, pre-releases included |

The default is Alpha while 3re itself is an alpha version. A version is newer by SemVer 2.0 precedence
(`2.10.0-alpha` > `2.9.1-alpha`; `2.10.0` > `2.10.0-alpha`). 3re never offers an older version.

## How an update is verified

Every release carries `update-manifest.json` and its minisign signature `update-manifest.json.minisig`.

1. The signature is checked with the public key built into 3re (`apps/update/release_key.hpp`, the same key as
   `tools/release/3re-update.pub`, key id `6EA665394615A750`): Ed25519 over the BLAKE2b-512 of the manifest, plus the
   signed trusted comment. A manifest that does not verify is ignored and nothing is downloaded.
2. The manifest says, in plain words (English and Arabic), what changed; 3re shows it before asking.
3. The package (`3re-<version>-windows-x64.zip`) is downloaded next to the install folder (`.3re-update\`); an
   interrupted download resumes. Its size and SHA-256 must match the signed manifest, or it is deleted.
4. The zip is unpacked and every file is checked against the signed list (size + SHA-256); a missing, changed or
   extra file stops the update. Paths are checked (no `..`, no absolute paths).

You can check a release by hand with the official minisign tool:

```
minisign -Vm update-manifest.json -p tools/release/3re-update.pub
certutil -hashfile 3re-<version>-windows-x64.zip SHA256
```

## How it is installed

3re starts `3re-update.exe` from the temp folder and closes. The updater waits for 3re to exit, then:

1. moves your files from the install folder into the new release: everything that the current `RELEASE.json` does
   not list — downloaded models and GPU libraries, the installer's uninstaller, files you added;
2. renames the install folder to `<folder>.previous` and the new release to the install folder (same drive, so each
   step is one rename, the same swap as `tools/package.ps1`);
3. runs `3re.exe --self-test`; if it fails, the new release moves to `<folder>.failed`, the previous one comes back
   and your files move back with it;
4. writes the result, which 3re shows at the next start, and starts 3re again.

Projects (Documents\3re\Projects) and settings are outside the install folder and are never touched.
**Settings → Updates → Go back to <version>** swaps the previous version back the same way.

Updating needs write access to the folder that contains the 3re folder. The installer installs per user
(`%LOCALAPPDATA%\Programs\3re`) for that reason; a copy under `Program Files` must be updated by hand.

## First-run downloads (AI models)

`app/models.json` (generated by `tools/release/make_models_catalog.py`) lists what 3re downloads instead of shipping:

| Pack | Size | From | Licence |
|---|---|---|---|
| GPU engine libraries (ggml, CUDA 12 runtime) | 642 MB zip | trellis.cpp v0.8.1 release | MIT; NVIDIA CUDA EULA |
| TRELLIS.2 weights, Q4 | 4.20 GB | github.com/3reusa7/3re, release weights-trellis2-q4-1 | MIT; dinov3.gguf: DINOv3 License |
| SAM 2.1 tiny, ONNX | 117 MB zip | huggingface.co/vietanhdev/segment-anything-2.1-onnx-models @ 6a3ac868 | Apache-2.0 |

Every file is pinned by size and SHA-256 at a fixed revision; archives are unpacked and each extracted file is
checked too. The dialog lists each pack's size, source and licence and needs "I have read these licences and accept
them" before anything downloads. Settings → AI models shows the state and re-checks every SHA-256 on request.

## For maintainers: signing a release

The signing secret exists only as the repository's Actions secret `THREERE_UPDATE_SIGNING_KEY` and in an offline
backup. The release workflow signs with `node tools/release/minisign.mjs sign` (Node's built-in Ed25519, no
packages). Replacing the key means every installed copy needs one manual update.

## Tests

`ctest -R update-` runs `update-core` (RFC 8032 / RFC 7693 vectors, a signature made by the Node signer, version
order, manifest refusals, the folder swap and roll-back, and the real `3re-update.exe`: an update from the previous
release and a roll-back after a failed self-test) and `update-flow` (a local server playing GitHub: update from the
previous release, bad signature, wrong key, corrupted download, failing release rolled back, resumed download, model
packs).
